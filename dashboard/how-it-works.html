Karma Leads: how it works

A tour of the machinery behind the leads dashboard — what runs where, how a lead gets from a spreadsheet or a LinkedIn search into the app, and which parts will bite you if you change them carelessly.

Companion documents: dashboard/README.md for using the dashboard, CLAUDE.md for the short version aimed at Claude Code.

The big picture

Three moving parts, all on one Windows machine. Nothing is hosted anywhere; the whole system is a Node process listening on port 8080 with a SQLite file next to it.

NocoDB supplies the database, the REST API, authentication and an admin UI. Everything the team touches day to day is the custom front end at /app, which is only an API client — it has no server of its own and stores nothing except a JWT and a few preferences in localStorage.

Why a custom front end at all? NocoDB's grid is a spreadsheet, and the whole point of this project was to stop looking at spreadsheets. The app is an email-style three-pane reader: list on the left, one lead open on the right, notes underneath.

The server, in full

index.js is ~110 lines and does exactly three things: serve the front end, register our own /app-api routes, then hand everything else to NocoDB. 

// static front end, with revalidation so a stale app.js can't half-load
app.use("/app", express.static(path.join(__dirname, "public"), {
  etag: true,
  setHeaders: (res) => res.setHeader("Cache-Control", "no-cache"),
}));

// our own routes — ALL must come before Noco.init or they never see a request
app.post("/app-api/import",     express.raw({ type: "*/*", limit: "80mb" }), …);
app.post("/app-api/job-search", express.json({ limit: "64kb" }), …);
app.get ("/app-api/apify-usage", …);              // credits for the ⚙ panel
app.get/post/delete("/app-api/recents", …);       // the Recent trail

app.use(await Noco.init({}, httpServer, app));   // 3-arg form; Noco.init({}) crashes
Order matters. Noco.init installs a catch-all router. Any route registered after it is unreachable — you'll get NocoDB's 404 instead of your handler.

Every /app-api route requires the caller's own xc-auth JWT and acts as that user, so NocoDB's permissions still apply to anything these routes write. The routes exist for the three jobs the REST API can't do: parsing a spreadsheet, holding a secret, and keeping a per-person activity trail.

The app folder sits outside OneDrive deliberately: noco.db is a live SQLite file, and cloud-syncing a database that's being written to is a good way to corrupt it.

The data model

One NocoDB base, Karma Leads, with five tables. The split into companies-versus-people is the core design decision: a lead you call by company name and a lead you call by a person's name need different fields and different handling.

TableRowsPrimary valueLinks
Companies32,888Company People here, Job postings, Similar companies
People2,305Name Company record
Job Board84Job Title Company record
Segments225Segment Companies
Blocklist531Phone—

The sixth table isn't in NocoDB

Every lead carries a Lead Code — KL-6KS2GV1FR4 — and the mapping lives in a separate SQLite file, lead_registry.db, outside the base entirely. That inversion is the point: noco.db is now a projection, and the registry is the system of record.

TableHolds
lead lead_code (PK), entity type, first/last seen, merged_into
lead_key (entity type, key type, key value) → lead_code — every natural key a lead ever arrived on
lead_work status, owner, favourite, notes — the team's judgement
lead_note record comments, keyed by code rather than row id

The code is deliberately opaque. It is Crockford base32 — no I, L, O or U, so it survives being read down a phone — and it encodes nothing: no name, no phone number, no row id, not even the entity type. A key made of data breaks the moment the data is corrected, which is the entire reason surrogate keys exist. Entity type lives in a column precisely because a lead can move between Companies and People when a source changes its mind about whether Lead differs from Company; baked into the key, that move would orphan the identity.

When two codes turn out to be one business, the older survives and the other is tombstoned via merged_into, never deleted — so a code someone pasted into a URL or a spreadsheet six months ago still resolves.

How "similar companies" works

There is no similarity algorithm. A Segment is just a Category × State bucket — stored as Restoration · FL, shown as Restoration · Florida — and every company is linked to exactly one. Opening a company and clicking through to its segment gives you every other company in the same trade and state. Cheap, obvious, and it needs no maintenance.

The reading pane shows six of them as a preview; the segment tag beside the heading opens the whole bucket as a paged view — see the segment view.

The front end

public/app.js — about 1,800 lines of plain JavaScript, 80 functions, no framework, no build step, no dependencies. Edit it and refresh. All state lives in one object: 

const S = {
  token, me, baseId, tables,   // session + resolved NocoDB ids
  tab: "companies",            // which sidebar view
  q: "", status: "", state: "",// search + filters
  sort: "recent",
  list: [], page: 1, pageSize: 50, total: 0,
  sel: null,                   // the open lead
};

Almost every interaction follows the same shape: mutate S, call loadList(), re-render. There is no reactivity and no diffing — rendering is innerHTML from a template string, then re-attaching listeners.

Booting and discovery

  1. Sign in. login() POSTs to /api/v1/auth/user/signin and stores the JWT in localStorage. Every later request carries it as an xc-auth header.
  2. Discover. discover() looks up the base by title, then each table by title, then builds a {columnTitle: id} map per table. No id is ever hardcoded in the front end — a rebuild changes every id, and the app has to survive that.
  3. Reveal. Only once discovery succeeds does boot() hide the login screen. An account that authenticates but was never invited to the base gets told so, instead of being dropped into an empty app.
  4. Load. Counts for the sidebar and stat tiles, then the first page of the current tab.
The blank-page failure mode. index.html and app.js must be updated together, so they're loaded as app.js?v=N — bump N whenever either changes. If a browser mixes a cached old file with a new one, the wiring code looks for elements that don't exist. Wiring is best-effort now (the on() helper skips missing elements and warns), but the version bump is the actual fix.

That second chart is the one worth internalising: this is a calling list first and a mailing list second. Anyone planning an email campaign off the base is planning it against a third of it.

The rendering rules are deliberate, and worth keeping if you add a tile:

  • Meter tracks are a lighter step of the fill's own hue (--accent-soft behind --accent), not grey, so the state reads across the whole bar rather than just the filled part.
  • Every bar is labelled in words beside it. No value is carried by colour or bar length alone — which is also what makes the three composition hues safe for colour-blind readers.
  • The three categorical hues were validated, not chosen by eye, against this app's own light and dark surfaces; the dark set is re-stepped for the dark background rather than being an automatic flip.
  • Percentages are suppressed when the baseline is meaningless. The first version of "new this week" cheerfully reported a rise of 8,000%, because the previous week held exactly one lead. Under a baseline of 10 it prints the prior week's count instead.

Cost-wise it's ~26 count queries per refresh, all fired in parallel (about 0.3s against SQLite). countAllWith() skips tables that lack the column — the job board has an Email but no Phone, and asking NocoDB for a missing column is a 400 — and refreshCounts() coalesces concurrent calls so a bulk import doesn't fire the fan-out repeatedly.

Native controls need color-scheme. The filter dropdowns were unreadable in dark mode — white popup, near-white text. The cause wasn't our CSS: nothing told the browser the page was dark, so Chrome painted the OS-drawn popup light. :root{color-scheme:light} plus :root[data-theme="dark"]{color-scheme:dark} is the actual fix, and it repairs scrollbars and checkboxes at the same time. Styling option alone doesn't cover every browser.

Listing, paging, sorting

buildWhere() assembles NocoDB's filter string from the current state. Its syntax is idiosyncratic — parenthesised triples joined by ~and and ~or: 

// search "acme" + Florida + uncontacted, excluding removed leads
((Company,like,%acme%)~or(Email,like,%acme%)~or(City,like,%acme%))
  ~and(Status,eq,New)
  ~and((State,like,FL)~or(State,like,Florida))
  ~and(Removed,notchecked)

Two details in there are load-bearing:

  • Both state spellings. Our sources disagree — FL in one file, Florida in the next — so the filter always matches both. It uses like rather than eq because SQLite's = is case-sensitive on text while LIKE is not.
  • notchecked, not eq,false. NocoDB checkbox filters need checked/notchecked; (Removed,eq,false) silently matches nothing.

Sorting is declared once and resolved per table. @date and @name are placeholders, because the date column is Date Added on two tables and Posted on the job board, and the name column differs on all three: 

{ key: "certs", label: "Most certifications", field: "Certs", dir: "desc" }
{ key: "name",  label: "Name A–Z",            field: "@name", dir: "asc"  }

sortUsable() then hides any option whose column the current table doesn't have — that's why People has no "most certifications" and the job board has no "highest revenue".

Paging, and the union tabs

Ordinary tabs page straight against the API with limit and offset, using pageInfo.totalRows for the page count.

Favorites and Removed are different: they span three tables, and NocoDB has no cross-table query. So the app fetches enough rows from each table to cover the requested page, merges them, re-sorts locally with unionComparator(), and slices out the window. It's capped at UNION_MAX (1,000) rows per table — far beyond anything those views hold today, but it is a real ceiling if one of them ever grows.

Recent is an activity trail

Recent used to mean "added in the last 30 days" — a fact about the data, not about anything anyone did, and on a base built from years-old exports that made it a near-empty tab nobody opened twice.

It now holds the last 25 leads you personally touched, newest first: opened, starred, re-statused, re-assigned, or noted. It starts empty for a new account and fills as you work. Every one of those actions calls touchLead(), which POSTs to /app-api/recents and moves the lead to the top of your trail rather than duplicating it.

The trail lives server-side in recents.json, keyed by the email on the signed-in JWT, so it follows the person from laptop to laptop and never crosses accounts; localStorage only caches it so the tab paints before the round trip. Opening the tab looks the recorded ids back up — one request per table, an ~or chain of (Id,eq,N) — and quietly drops anything deleted or removed since. Twenty-five rows aren't worth a where clause, so search, state and status filter locally, and the sort control is disabled: the list has exactly one meaningful order.

Two details worth keeping: the write is fire-and-forget and never re-renders the list on its response, because reshuffling rows under someone's pointer is worse than being one entry stale; and writes on the server go through a single queue, or two quick clicks would read the same file and one would clobber the other.

The segment view

A seventh tab that never appears in the sidebar. Clicking the segment tag in a company's Similar companies block calls openSegment(id, label), which parks the id in S.segment, sets S.tab = "segment" and gives loadList() a third branch. Rows come from the Segments↔Companies link rather than the Companies table: 

GET /api/v2/tables/{segmentsId}/links/{colId}/records/{segmentId}
      ?limit&offset&fields&where

Two things about that endpoint decided the design:

  • It ignores sort. Not an error — it accepts the parameter and returns the same order regardless. So the sort control is disabled and reads Segment order, the same honesty the Recent tab uses. Don't re-add sort options here; they would appear to work and wouldn't.
  • It projects down to Id + the primary value unless you pass fields. The first version rendered a segment as a bare column of company names with no city, certs or date, because the endpoint simply hadn't sent them. SEGMENT_FIELDS asks for what renderList() draws, intersected with the columns the base actually has.

where is honoured, so the search box and the state and status filters keep working inside a segment — buildWhere("companies") is reused unchanged. Any sidebar tab clears S.segment through setTab(), and the ← beside the title does the same.

The reading pane

Clicking a row re-fetches the full record (the list only carries display fields) and renders:

  • Research buttons. Google gets the company plus its location, which is what separates one "ABC Restoration" from twelve others. LinkedIn branches: on a person it searches name + company in all-results; on a company or job it opens the Companies tab with the bare company name, because a city in the keywords loses the page.
  • Click-to-copy email. copyText() uses navigator.clipboard, which needs a secure context — fine on localhost, not over http://<lan-ip>, so there's an execCommand fallback and an honest failure toast.
  • Related leads. Follows the link columns: people at that company, its job postings, and its segment's other companies.
  • Notes. Loaded and posted through the record-comments API.

Getting data in

Four paths. Three of them must agree with each other: they each decide where a row belongs, what its phone key is, and whether it's a duplicate — using the same rules, implemented twice in two languages. The job search only ever writes job postings, so it plays by its own dedupe rules.

PathUse it forDestructive?
A — setup_v2.py changing the structure of the tables yes — recreates the base
A′ — sync.py refreshing from the source files. The everyday path. no — never deletes
B — the drop zoneone-off spreadsheetsno
C — 🔎 Find jobsfresh LinkedIn postingsno

Path A′ is the one that changed the character of this project. It reads the same files, forms the same clusters, resolves the same lead codes, then reconciles: new code → insert, known code → update only the fields that actually changed, code absent from the files → left alone. A blank in a file never blanks a populated cell, so a thinner export cannot strip detail a richer one supplied, and Status/Owner/Favourite/Notes are never written — a spreadsheet has no opinion about whether you have qualified someone.

Nothing is ever deleted, deliberately. A lead vanishing from an export means the export changed, not that the business closed — and someone may have spent a week working it. Removal is a decision a human makes with the 🚫 button. It is not something a refresh should infer.
Change one, change the other. dashboard/setup_v2.py and karma-leads-nocodb/import-leads.js are ports of the same logic. If they drift, an imported lead and a rebuilt lead end up in different tables, and the blocklist stops being reliable.

Path A — the full rebuild destructive

python dashboard/setup_v2.py
  1. Parse. collect() in setup_and_import.py is a hardcoded manifest of file → parser → category. Six parsers cover the six export shapes. Adding a new source file means adding a line here.
  2. Split. Job-board rows go to jobs; a row whose person name differs from its company goes to people; everything else is a company.
  3. Dedupe via the ladder below, merging non-empty fields into the kept row.
  4. Create the five tables, insert in batches of 100, then link people and jobs to companies by normalised name and every company to its segment.
  5. Build views (main list, Recent 30d, ⭐ Favorites, 🚫 Removed — these are the NocoDB admin views, not the app's own tabs) and hide the cluttered columns. Table and column ids are written to dashboard/nocodb_ids.json.

Statuses, owners, notes, comments, favourites and every member's invitation are destroyed by this. The one exception is the blocklist: it's read out of the live table first and restored afterwards, and any lead matching a banned number comes back already removed.

The token never reaches the browser. It lives in karma-leads-nocodb/apify_token.json and is read server-side per request. Knowing the cost

Billing is per job returned. Two figures matter, and they are different figures:

WhenWhat we showWhere it comes from
Before the run A maximum — limit × rate Live rates via actorRates(). It's a ceiling: you only pay for jobs actually returned, so a search matching nothing costs nothing.
After the run The actual charge found × rate + the flat start event, computed locally.
Any time Credits used / remaining, and a daily-spend chart GET /app-api/apify-usage → Apify's /users/me/limits and /usage/monthly.
Read the price from the actor, not from the docs. The store page advertised "$1.50 per 1,000"; the actual charged event price is $5.00 per 1,000 ($15 with recruiterOnly). actorRates() reads the live pricingPerEvent off the actor and caches it for six hours, so a vendor price change updates the estimates instead of quietly making them wrong. The hardcoded rates in RATES are only a fallback.
Why not just read usageTotalUsd off the run? Because it lags. Apify's own run and account figures settle five to fifteen seconds after the run finishes, which is longer than anyone will stare at a result panel. Computing the charge from the returned count is exact and immediate; the reported figures are kept only as an upward cross-check.

The default search

JS_DEFAULTS in app.js ships the standard prospecting search, so the button is one click rather than a form: back-office titles (office admin, estimator, bookkeeper, billing specialist…) crossed with restoration description keywords (water damage, Xactimate, IICRC…), US-wide, last 7 days, full-time, agencies hidden, and organizationEmployeesLte: 200 — a small firm hiring an office administrator is the pitch.

Defaults merge with ??, not ||, which is the whole trick: a field the user deliberately emptied and saved stays empty, while a field they never touched still gets its default. Reset clears the key to get them back.

The five algorithms

Four of these decide where a lead belongs and whether we've seen it before; the fifth does the same job for job postings, which carry no phone number.

1 · Where does this row go?

if      (job file)                    → Job Board
else if (name && company && name !== company) → People
else                                  → Companies

Deliberately blunt. A row that names a person and their employer is a person; a row that only names a business is a company. Rows where the two columns hold the same string — common in CRM exports where a sole trader is their own company — are companies.

2 · Is this a duplicate?

This used to be a ladder — email, else phone, else name+city, first match wins. That was wrong in both directions at once, and finding out why is the most interesting thing in this document.

Too strict. Each row picked one key. Vendor Leads 1216.csv carries no email column at all, so all 15,638 of its rows keyed on phone; Bitrix Vendor Leads 1007 keyed 100% on email. Those two files could never collide by construction, however much they overlapped.

Too loose. Email was treated as identity. But t.braun@servpro.com — one regional manager — sits on nine separate SERVPRO franchises with nine different phone numbers. The ladder keyed all nine on that address and collapsed them into a single row, erasing eight real businesses. Separately, phone_digits accepted 7-digit fragments and Bitrix placeholders as keys, silently losing another 69 rows.

It now unions on any agreeing key, with three guards. The guards are the whole design: franchises are not duplicates.

KeyMerges when……unless
Phonealways — strongest signal the names and emails both disagree. A number mistyped onto someone else's row is the one way a phone lies — Willies Shoe Repair and Williams Wooden Floor Company share one in the source.
Emailthe names also agree the cities conflict. Same brand, two towns, two branches.
Name + citythere is a real city the phones disagree — unless the source itself said “X DBA Y”.

aliases() is what finally lets the master sheet meet the vendor files. The master lists the franchisee's legal entity (Arma Hawk, Llc / Dba Servpro Of Alexandria); the Bitrix exports list the trading name (ServPro of Alexandria). Splitting on DBA indexes both halves. Names that normalise to a bare trade word are dropped — norm_co() strips pc wherever it appears, so “Pc Restorations” comes back as “restorations”, which would match half the industry.

The net effect on the count was 48 rows. That is the honest headline, and it is nearly nothing. What actually changed is which rows: 198 true duplicates went away and 150 real businesses came back. The total barely moved and is now made of the right records.
One business can still legitimately appear twice: same name, same city, two different valid phones, no DBA evidence. RAM Restoration in Grand Rapids is in there twice from two Apollo exports. That is the guard working as designed — it errs toward keeping, because the cost of wrongly merging two franchises is higher than the cost of one visible duplicate. Base-wide that residual is 117 groups / 133 rows (0.4%).

3 · Is this number bannable?

The most dangerous code in the project. Removing a lead bans its number and sweeps every table — so a bad key means one click wipes out dozens of good leads. 

function pk(phone) {
  let d = digitsOnly(phone).slice(-10);
  if (d.length !== 10)                      return null;  // not a US number
  if (d[0] === "0" || d[0] === "1")         return null;  // impossible area code
  if (new Set(d).size <= 2)                 return null;  // 9000000000-style filler
  if (d.slice(3) === "0000000")             return null;  // same
  return d;
}
Do not loosen these checks. The Bitrix exports are full of placeholders like +119000000000 shared by up to 46 unrelated companies. Rejecting them entirely is why banning a number is safe. A lead with no key removes only itself.

As a second line of defence, the remove dialog counts the blast radius and shows it before you confirm — some franchise and toll-free lines really are shared by several businesses.

4 · When was this lead added?

OneDrive rewrites file modification times, so those are worthless. Instead the date comes from the MMDD token in the filename — Apollo Mobile Export 0428.csv → 28 April — with months 1–7 read as 2025 and 8–12 as 2024, matching the verified timestamps inside the files. Files with no token get a blank date, which is why some leads never count towards "New this week" and never sort to the top under "Newest first". Imported files just get today.

5 · Is this job already on the board?

Job postings have no phone and usually no email, so the ladder above has nothing to work with. Jobs get their own identity:

  1. Job URL, with the query string and trailing slash stripped — the posting's own address, and the reliable key.
  2. Title + company + city, lowercased — because LinkedIn re-posts one opening under several job ids, and the vendor's own docs recommend fuzzy matching on title + organisation for exactly this reason.
Don't dedupe on ats_duplicate. The actor returns that flag, and it reads like "this is a duplicate" — it isn't. It means the posting also appears in the vendor's other dataset, which says nothing about the results in front of you. An early version skipped those rows and threw away half of every search: ten jobs found, five silently discarded.

NocoDB's sharp edges

EdgeWhat happens
Bulk insert cap More than 100 records per POST returns 422 ERR_MAX_PAYLOAD_LIMIT_EXCEEDED. Everything batches at 100.
Checkbox filters Need checked/notchecked. (Favorite,eq,true) matches nothing, silently.
Two link types A link column created on the parent is Links; the mirror auto-created on the child is LinkToAnotherRecord. Code that scans for links must accept both — missing this silently skipped a rename during development.
Linking direction Link from the parent side to attach many children in one call.
Server startup Noco.init({}, httpServer, app) — the 3-argument form. Noco.init({}) alone throws.
Ids are not stable Every rebuild issues new base/table/column ids. The front end resolves them by title at runtime; only the Python scripts read nocodb_ids.json.

Changing things safely

Adding a field to the app

  1. Add the column in setup_v2.py so rebuilds keep it.
  2. Map it in import-leads.js if a spreadsheet can supply it.
  3. Render it in renderDetail() or factsHtml().
  4. Add a SORTS entry if it's worth sorting by — the option auto-hides on tables without the column.
  5. Bump ?v= in index.html.

Adding a new source spreadsheet

For a one-off, just drop it on the app. To make it part of rebuilds, add a line to collect() — reusing an existing parser if the columns match, which they usually do.

Changing the job search

  1. New actor input? Add it to the whitelist in buildInput() (job-search.js) and to the request body in runJobSearch() — a parameter the server doesn't know about is dropped silently, which looks exactly like the filter not working.
  2. Add the control to openJobSearchSettings(), its key to jsSettings()/collect(), and a default to JS_DEFAULTS if it should be on out of the box.
  3. Show it on the confirm screen if it changes what gets searched or what it costs. That screen is the last thing between a click and a charge.
  4. Bump ?v= in index.html.
Test with limit: 10. Every test run is billed, and the actor's minimum is 10 — about 5¢ a go.

Before you run a rebuild

Copy the app folder first. A rebuild discards every status, note, owner, favourite and member invitation in exchange for re-reading the files, and there is no undo. Ask whether the drop zone would do the job instead.

Building one of these

A walkthrough for someone comfortable with pandas and SQL who hasn't shipped a team-facing data tool before. Every phase below names the decision, the reason, and what this project actually got wrong first.

The through-line: a lead database is not an analysis, it's an operational system. Analyses are read-only, single-user, and finished. This is written to by several people, forever. Almost every decision below follows from that one difference — and it is the difference a notebook-shaped instinct will miss.

1 · Profile the data before you design anything

Resist opening a schema designer. Load every file, concatenate nothing, and count: rows per file, non-null rate per column, distinct values per column, and the top 20 values of anything you plan to key on or filter by.

What that surfaced here, none of which was in anyone's head beforehand:

  • Firmographic coverage varies by source, not at random — Apollo rows have headcount ~90% of the time, Bitrix rows ~2%. Any "average company size" across the whole base is meaningless.
  • States are spelled two ways (FL and Florida) because different exporters disagree. Group by state naively and you get two of everything.
  • Bitrix writes numeric internal IDs into City, State and Industry columns. They look like data and are not.
  • A licence column that looked like a trade classifier was mostly bare codes — HIC, CGC, B.
What it cost to skip: nothing here, because it was done first — but every one of those four would have become a schema decision that had to be unwound later. Profiling is the cheapest hour in the project.

2 · Let the data pick the schema, not your ER instincts

Version one of this project was a single flat Leads table — every row from every source, one wide schema. It worked, and it was wrong: it read like a spreadsheet, which was the exact thing the project existed to escape. Half the columns were empty for any given row, because a company lead and a person lead genuinely need different fields.

The split came from a property already present in the data: a row that names a person and their employer is a different kind of thing from a row that only names a business. That one test produces the whole model — Companies, People, Job Board — and it is three lines of code: 

if   is_job_export(file)                          → Job Board
elif name and company and name != company        → People
else                                             → Companies

The name != company guard matters: CRM exports of sole traders put the same string in both columns, and without it every one-person business becomes a fictional person.

What it cost: one full rewrite (v1 → v2). Cheap here because no one was using it yet. Do this before humans start entering data, not after.

3 · Identity and dedupe — the part that will actually hurt

Merging lead lists is a record-linkage problem wearing a friendly hat. There is no shared key across sources, so you build a ladder of decreasingly trustworthy ones and take the first that fires:

  1. Email — reliable when present
  2. Phone, normalised to the last 10 digits
  3. Name + city — the fallback when there's no contact detail at all

The lesson worth carrying to your next project is the trap underneath this. A key is only a key if it is actually unique, and you must check rather than assume. Here, one Bitrix placeholder number (+119000000000-style) was shared by 46 unrelated companies. Keying on it would have meant one "do not call this number" click silently deleting 46 good leads.

So before trusting any key, run the cheapest possible diagnostic — value_counts() on it and look at the top of the distribution: 

# if your "unique" key has a fat head, it isn't one
df.groupby(phone_key).size().sort_values(ascending=False).head(20)

Anything with an implausible count is a placeholder, a switchboard, or a parsing bug. The fix here was to refuse to generate a key at all for numbers failing a validity test (bad area code, ≤2 distinct digits, seven trailing zeros) — see algorithm 3. A record with no key is honest; a record with a wrong key is contagious.

What it cost: nothing, because the distribution check caught it. Had it shipped, the damage would have been silent and gradual — the worst kind.

4 · Choose the storage layer by who writes to it

The instinct is a notebook plus a Parquet file, and it is wrong here for one reason: the team writes back. Statuses, owners, notes, favourites, do-not-call flags. The moment humans produce data, you need concurrency, durability and access control, and you have left analysis-land.

OptionWhy not / why
Notebook + Parquet/CSV No concurrent writes, no auth, no referential integrity. Fine for the profiling in phase 1; unusable as the system of record.
Shared spreadsheet What the team was already escaping. Lost edits, no types, no joins.
Postgres + a web app you write Correct, and the most work: you own auth, migrations, an admin UI and a REST layer before you show anyone anything.
NocoDB on SQLite chosen Gives the database, a REST API, authentication, permissions and an admin UI for free. You inherit its quirks (see sharp edges) but skip weeks of plumbing.

The general principle: for internal tools, buy the boring layers and spend your effort on the part that is specific to your problem — here, the parsers and the dedupe. Nobody will thank you for a hand-rolled login page.

5 · Write the pipeline so it can run twice

Structure it as parse → clean → route → dedupe → load, with each stage a pure function you can test on one file. The parsers are the only part that should know a source's quirks; everything downstream sees a normalised dict.

Three things to build in from the first commit, not retrofit:

  • Idempotency. Re-running must be a no-op, not a duplicate. Every loader here checks what's already present first. The DNC importer is the clearest case — run it monthly and it applies only the difference.
  • A dry run. Any script that mutates shared state should be able to print exactly what it would do. This is what makes a destructive operation reviewable instead of a leap of faith.
  • Batch limits. Every API has one. NocoDB rejects more than 100 records per insert. Discover that in a helper, once, rather than in five call sites.
What it cost: the rebuild script wasn't idempotent — it deletes and recreates — which is why running it destroys statuses, notes and member invitations. That constraint has shaped every decision since, and is why the additive drop-zone importer exists at all.

6 · The interface is where adoption is won or lost

NocoDB ships a perfectly good grid. The team wouldn't use it, because a grid of 33,000 rows is a spreadsheet, and they had one. The custom front end is an email-style three-pane reader: list, one record open, notes underneath — a shape people already know how to use.

Two engineering choices that paid off repeatedly:

  • Resolve IDs at runtime by name. Every rebuild issues new base/table/column IDs. The front end looks everything up by title on boot, so a rebuild doesn't break it. Hardcoding IDs would have meant editing the app after every rebuild.
  • No build step. Plain HTML/CSS/JS, edit and refresh. For a single-team internal tool the entire npm toolchain is a tax with no return — and it means anyone can fix a label without a node install.
What it cost: one whole-app outage class. Because index.html and app.js must change together, a browser caching one and not the other threw during wiring and rendered a blank page. Hence the ?v=N cache-bust discipline.

7 · Paid enrichment: treat the API key like money

Bolting on a paid data source (here, LinkedIn jobs via Apify) introduces a failure mode analysis code never has: a bug can spend real money. The rules that fell out of it generalise to any metered API:

  • The key never reaches the browser. It lives server-side and the client posts parameters, never a request. Otherwise every teammate's dev tools is a spending console.
  • Rebuild the request from a whitelist. Don't forward what the client sent. That is what enforces the result cap.
  • Show a ceiling before, the actual charge after. Never let someone click a button whose cost they can't bound.
  • Read prices from the API, not the docs. The store page advertised $1.50 per 1,000; the real charged event price was $5.00. Anything you hardcode from documentation is a number that will quietly go stale.
  • Validate the vendor's flags against reality. An ats_duplicate field read like "this is a duplicate" and actually meant "also present in our other dataset". Trusting the name silently discarded half of every search.

8 · The operational half nobody teaches

A shipped tool needs care that no course covers. The three that bit hardest here:

  • Watch the database's own exhaust. NocoDB logs every insert and every link to an audit table with the full row JSON inline. Loading 35k rows and linking them wrote ~180 MB per rebuild. The file reached 1.3 GB holding 7 MB of leads — a 185× overhead, invisible until someone checked the folder size.
  • "Delete" often isn't. Deleting a base in NocoDB sets deleted=1 and leaves every physical table and row in place. Seven dead bases had accumulated, including five complete copies of the Companies table.
  • SQLite doesn't shrink on its own. Deleting rows moves pages to a freelist; the file stays the same size until you VACUUM, which needs exclusive access. Cleanup took the file from 1,296 MB to 11 MB.

The habit worth forming: periodically measure the thing, not the code. Row counts, file sizes, key distributions, response times. Every problem in this list was invisible in the source and obvious in one measurement.

If you're rebuilding this from scratch, the order that would have saved the most time: profile (1) → identity rules and their distribution check (3) → schema (2) → smallest possible loader with a dry run (5) → put it in front of a user → only then the interface (6). The interface is the fun part and the least likely to be wrong; the identity rules are the boring part and the most expensive to get wrong.

Going live: hosting, roles and what it costs

Everything above assumes one machine on a desk. Putting it in front of ~50 people a day changes five things, in rough order of how quickly they bite.

What breaks the moment you deploy

  1. The port is hardcoded. index.js calls app.listen(8080). Render injects a PORT environment variable and health-checks that port — this alone fails the deploy. app.listen(process.env.PORT || 8080).
  2. The filesystem is ephemeral — the one that actually matters. noco.db and lead_registry.db are files on disk. On a standard Render service every deploy and every restart wipes them. That takes the database and the identity registry with it, and the registry is the one thing here that cannot be regenerated. Two ways out, below.
  3. Secrets are files. apify_token.json and api_token.json are read with fs.readFileSync, and both are gitignored — so neither exists in the deployed container. They need an environment-variable path with a file fallback. admin_credentials.json already does this correctly; copy that pattern.
  4. The Python importers have nowhere to run. They read from a OneDrive folder that does not exist on a server. Leave them local and point them at the hosted API — the raw exports are real names, phone numbers and a do-not-call list, and keeping them on one workstation instead of a hosted disk is a feature.
  5. One thing that gets better: hosting is HTTPS, so navigator.clipboard works and the execCommand fallback stops being load-bearing.

Admin mode and user mode

Most of this already exists and is simply unused. NocoDB owns authentication and roles, the front end signs in against it, and app.js already fetches /api/v1/auth/user/me into S.me — it just never reads the roles it gets back. Record-level permissions are genuinely already enforced, because both the app and the drop-zone import use the caller's JWT rather than the API token.

RoleSees
Owner / Creator — admin the NocoDB admin UI at /dashboard, spreadsheet import, blocklist management, 🔎 Find jobs
Editor — the team /app: work leads, set status, owner, notes, favourites
Commenter / Viewerread-only
There is one real hole, and it is a budget leak. /app-api/job-search checks only that a JWT exists — not what role the caller holds — and then spends your Apify token at $5 per 1,000 results. With one user on localhost that is fine. With 50 logins it is an uncapped spend that anyone can trigger. The fix is small: recents.js already shows the pattern — ask /api/v1/auth/user/me with the caller's own JWT and reject non-admins. Do it server-side; hiding the button in the front end is cosmetics, not a control.

What it costs

Fifty daily users is perhaps 8–12 concurrent, and the whole dataset is 13 MB. The cost driver is NocoDB's own memory footprint, not your data — it idles around 300–500 MB before serving anyone.

Lean — SQLite on a persistent diskSafe — managed Postgres
Web service (2 GB)$25$25
Persistent disk (5 GB)~$1—

Plus Apify, which is usage-based and should be admin-gated: a few searches a week is roughly $5–20/month. Call the whole thing $30–50/month. Those hosting figures move — check current pricing rather than trusting this table.

  • Don't use a free tier. It sleeps after inactivity and the team eats 30-second cold starts all day.
  • 512 MB is too tight for NocoDB. 2 GB is the safe floor.
  • No licence cost. Self-hosted NocoDB is unlimited users; only their cloud charges per seat.
Take the SQLite-plus-disk path. For this many users it is the right engineering call rather than a compromise: the load is read-dominated and well within SQLite's range, and it avoids migrating NocoDB's entire metadata database to Postgres — the difference between an afternoon and a week. What you accept: a single instance, ~30–60 seconds of downtime per deploy, and a disk that is a single point of failure. Since lead_registry.db lives on it, turn on snapshots and pull a copy off-platform on a schedule. Nothing in the app knows which database is underneath, so Postgres stays available later.
One thing to decide deliberately rather than by accident. The .gitignore is careful that real names, phones, emails and a do-not-call list never reach GitHub. Deploying puts that same data on someone else's infrastructure behind a single password. That is a normal and defensible thing to do — but it changes your exposure, and it is worth thinking about enforced strong passwords or SSO, who genuinely needs Editor rather than Viewer, how long the DNC list is retained, and what you would owe people if it leaked.

Now it unions on any agreeing key and guards each one: email needs the names to agree too, phone yields when names and emails both disagree, name+city yields to a phone conflict unless the source said "X DBA Y". That last part is what finally lets the master sheet's legal entities meet the vendor files' trading names.   • 2026-08-04
    Two thirds of the base gets its state back data quality
    The same investigation turned up a quieter problem: 68% of companies had no State. The Bitrix exports put unresolved picklist IDs (7318) in that column and clean_place() drops them, so Vendor Leads 1216.csv — 15,638 rows, nearly half the base — was invisible to the state filter and sat in a blank-state segment. backfill_states() fills it from the row's own city where that city means one state in this corpus, and otherwise from the geographic NANP area code. City goes first because it is the row's own location field, where the phone may be a mobile or a head-office line. Blank states fell from 68% to 5%. It is inference, not data: measured against a held-out 30% of the rows that do carry a state, it covers 86% of them and gets 96% right.
  • 2026-08-04
    Leads get a permanent code architecture
    The question "was that dedupe work worth it?" had an uncomfortable answer: not really — but it exposed something that was. setup_v2.py drops the base and recreates it, and NocoDB row ids are positional, so every rebuild renumbered every lead. Statuses, owners and notes were destroyed, recents.json silently pointed at different companies, and every deep link went stale. Fixing a data bug and keeping the team's work were mutually exclusive — and the only reason that had never hurt was that nobody had done any work yet. The trap was closing quietly.

    So every lead now carries a Lead Code — KL-7QX4M2H8ZB, opaque on purpose, encoding no name, no phone and no row number, because a key made of data breaks the moment the data is corrected. A separate lead_registry.db remembers every natural key a lead ever arrived on, so a rebuild can find it again; statuses, owners, favourites and notes hang off the code rather than the row. When two codes turn out to be one business the older one survives and the other is tombstoned, never deleted, so an old code in a URL still resolves. sync.py is the new everyday path: it inserts what is new, updates only fields that actually changed, and never deletes — a lead vanishing from an export means the export changed, not that the business closed.

    Three bugs surfaced only because the test asserted codes were byte-identical across three consecutive runs. A contact shares their employer's phone number, so people were inheriting company codes and stealing their keys — 243 codes drifted. Keys were being overwritten rather than left alone, so two leads sharing one could churn forever. And the nine SERVPRO franchises on one manager's email — the ones the dedupe guards correctly refuse to merge — could never find themselves again afterwards, minting a fresh code every run and leaking their work. Measured after the fixes: a 15,638-row export landing on a 19,145-row base left 17,374 of 17,382 codes untouched, and all work product survived.

Dropped and VACUUMed back to 13.3 MB. The lesson stands: this happens on every setup_v2.py run, which is one more reason sync.py is now the everyday path. recents.json was cleared too — row ids changed, and a stale trail points at the wrong companies rather than at nothing.
