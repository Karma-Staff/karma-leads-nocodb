KarmaLeads · Ops runbook

From one Windows PC to the cloud

Moving Karma Leads to Render

Right now the whole system lives on one computer: if it sleeps, the team's dashboard sleeps. This guide moves the dashboard and its database to Render — a hosting service that runs them for you — while deliberately keeping the sensitive parts (raw lead files, the do-not-call list, the identity registry) on your machine. It covers what to do, what can go wrong, and how to pace it over one week.

Cost ≈ $13–15 / month Hands-on work ≈ 4–6 hours Calendar time 1 week (parallel run) Written Aug 11, 2026
01

The big picture: what moves, what stays

A migration is only scary when you're not sure what's actually moving. Here, exactly two things move to Render: the web app (the Node server in server/ plus the pages in public/) and the PostgreSQL database (every lead, user, note, and activity row). Everything privacy-sensitive stays on your PC on purpose.

Stays on your PC

The import pipeline

  • Raw lead exports (real names, phones)
  • The do-not-call list
  • lead_registry.db — the identity store
  • sync.py / import_dnc.py

Secret files

  • apify_token.json, .env.server
  • None of these are in git, none deploy
HTTPS +
service token
Moves to Render

Web service (Docker)

  • server/index.js — the API + the app pages
  • Runs migrations on boot, then serves
  • Sign-in via WorkOS (already live)

Managed PostgreSQL 17

  • Database karma — the system of record
  • Daily backups handled by Render

Why this works: after the August re-architecture, the web app is stateless — a fancy word meaning the server itself remembers nothing between restarts. Every fact lives in Postgres; uploaded import files are parsed in memory and written straight to the database; your login is a sealed cookie in the browser. Render restarts and redeploys containers whenever it wants, and a stateless app genuinely does not care. The old design (a SQLite file on disk) would have lost data on every deploy — that's the design you already migrated away from.

What deliberately does not deploy: the NocoDB admin grid (it needs a second database Render's single-database plans can't host — defer it), Caddy (Render provides HTTPS itself), and the old legacy server (already retired at the WorkOS cutover).

02

Where you stand: solved, and honest faults

An earlier deploy review found five blockers. Most were already fixed by the re-architecture; the rest were patched this week. What remains on the right is the honest list of weaknesses — none blocks the migration, but you should know them by name.

Already solved

  • Port: the server reads process.env.PORT, which Render injects.
  • Ephemeral disk: all state is in Postgres; nothing the server writes to disk matters.
  • Secrets: every token now reads the environment first, files as local fallback.
  • Importers: they already talk to the API over HTTPS with a scoped token — never to the database directly.
  • Auth: WorkOS cutover is done; the legacy sign-in server is deleted.
  • Docker image: installs @workos-inc/node, runs migrations before serving.
  • Clipboard: HTTPS hosting makes navigator.clipboard work everywhere.

Honest faults to manage

  • One-machine bus factor.Imports, the registry, and all the know-how live on a single Windows PC. If it dies, imports stop (the dashboard keeps running). Back up lead_registry.db off the machine.
  • No tests, no staging.Every deploy is trust-based. Mitigation: the parallel-run week below, and --dry-run before every import.
  • Step 6b is unfinished.Lead identity still resolves through the local SQLite registry, which is why imports must keep running on your PC for now.
  • No hosted admin grid.NocoDB stays local-only. Admin data edits away from your PC happen through the app itself.
  • Session cookie lacks the Secure flag.Harmless behind Render's HTTPS, but a two-line hardening worth doing later.
  • Off-site backups are a habit, not a system.Render backs up daily, but the lead codes can never be regenerated — keep your own weekly dump too (Phase 6).
03

The migration, phase by phase

Each phase ends with a checkpoint — a way to prove it worked before moving on. If a checkpoint fails, stop and fix; nothing in later phases can repair an earlier one. Commands are PowerShell, run from the repo folder.

0

Prepare (nothing changes yet)

≈ 30 min · zero risk

Confirm the repo is pushed to GitHub with no secrets in it (they're gitignored — verify with git status that .env, .env.server, and the token files are untracked). Have your WorkOS dashboard login and Render account ready. Pick the Render region closest to the team and stick to it — the database and web service must share a region to talk over the fast internal network.

Checkpoint: git log on GitHub shows your latest commit; no secret file appears anywhere on github.com.
1

Create the database

≈ 15 min

Render → New → PostgreSQL. Version 17 (matching local), database name karma, smallest paid instance. Paid is not optional: Render's free Postgres is deleted after 30 days, and this database will hold lead codes that cannot be regenerated. When it's created, Render shows two connection strings — internal (only reachable from your Render services; the app will use this) and external (reachable from your PC; you'll use it for loading data and admin).

Checkpoint: from your PC, psql "<external URL>" -c "select 1" answers. If it complains about SSL, add ?sslmode=require to the URL.
2

Copy your data up — before the first deploy

≈ 30 min

Your local Postgres is already the system of record, so this is a plain dump-and-restore, not a re-run of the old migration script. The order matters: restoring first brings the _migrations table along, so when the app boots on Render and runs server/migrate.js, it correctly sees everything already applied instead of fighting the restored schema.

# dump the karma database out of the local Docker Postgres
docker compose exec db pg_dump -U postgres -d karma -F c -f /tmp/karma.dump
docker compose cp db:/tmp/karma.dump .\karma.dump

# restore it into Render (external URL, with sslmode=require)
pg_restore --no-owner --no-privileges -d "<external URL>?sslmode=require" .\karma.dump

--no-owner --no-privileges matters because Render gives you one database user, not the karma_api / nocodb_admin role setup from Docker — ownership statements from the dump would otherwise fail. That role separation existed mainly to fence in the NocoDB container, which isn't coming along.

Checkpoint: psql "<external URL>" -c "select count(*) from leads" matches your local count.
3

Create the web service

≈ 45 min

Render → New → Web Service → pick the GitHub repo. Runtime: Docker (the repo's Dockerfile already does the right thing). Instance: Starter. Then two settings people miss: set the health check path to /app/ — the site's root / answers 404, and Render would conclude the app is broken and loop the deploy — and add the environment variables:

VariableValueWhat it is
DATABASE_URLthe internal connection stringHow the app reaches Postgres. Internal, not external — see risk list.
WORKOS_API_KEYsk_… from WorkOSThe sign-in system. Same values as your local .env.server, except the redirect URI, which must be the Render URL.
WORKOS_CLIENT_IDclient_…
WORKOS_REDIRECT_URIhttps://<app>.onrender.com/api/auth/callback
SESSION_SECRETa long random string
APIFY_TOKENthe Apify keyPowers the admin “Find jobs” button.

Leave NOCODB_ADMIN_URL unset — there is no hosted NocoDB, so the admin menu's link simply goes nowhere for now. Don't set PORT; Render injects it.

Checkpoint: the deploy log shows migrations reporting nothing to apply, then “Karma Leads API on …”. The service shows Live.
4

Tell WorkOS about the new address

≈ 10 min · the step everyone forgets

WorkOS only redirects sign-ins to URLs it has been told to trust. In the WorkOS dashboard → Redirects, add https://<app>.onrender.com/api/auth/callback — character-for-character identical to the env var, alongside the existing localhost one (keep that; your local runs still use it).

Checkpoint: open https://<app>.onrender.com/app/, sign in with your own account, and land on the dashboard with correct lead counts.
5

Point the import pipeline at the cloud

≈ 30 min

The importers stay on your PC — that's the privacy feature, not a compromise. They just need two environment variables changed to aim at Render instead of localhost. Mint a fresh service token so the hosted app has its own credential you can revoke independently:

# mint a pipeline token against the HOSTED database
$env:DATABASE_URL = "<external URL>?sslmode=require"
node server/cli.js token:create pipeline imports:write   # copy the klsvc_… once — it's shown once

# aim the pipeline at Render and rehearse
$env:KARMA_API_URL   = "https://<app>.onrender.com"
$env:KARMA_API_TOKEN = "klsvc_…"
python dashboard/sync.py --dry-run    # ALWAYS first; read the plan it prints
python dashboard/sync.py
Checkpoint: the dry-run's insert/update numbers look sane (a full re-run against just-restored data should be nearly all no-ops), and after the real run the import appears in the Team activity tab.
6

Make backups a habit

≈ 20 min, then automatic

Render keeps daily backups, but platform backups protect you from Render's disks failing — not from an account mistake, a bad import, or Render itself. Keep your own copy of the two things that can never be rebuilt: the database (it holds every lead code) and lead_registry.db. A Windows Scheduled Task running weekly is enough:

pg_dump "<external URL>?sslmode=require" -F c -f karma-$(Get-Date -Format yyyyMMdd).dump
Copy-Item lead_registry.db "$env:OneDrive\backups\lead_registry-$(Get-Date -Format yyyyMMdd).db"
Checkpoint: you have restored one of these dumps into a scratch database once. A backup you've never restored is a hope, not a backup.
04

Where it can go wrong

Every one of these is predictable, which means every one is survivable. Severity: blocks deploy stops you cold, data risk can cost real information, annoyance wastes an afternoon.

Deploy loops forever, app never goes Live

blocks deploy

Render polls the health check path and restarts the app when it doesn't answer 200. The site root / is a 404 by design (the app lives at /app/).

Fix: set the health check path to /app/ in the service settings.

“no pg_hba.conf entry” / “SSL required” when connecting from your PC

blocks deploy

Render's external connections require encryption; psql, pg_dump, and pg_restore won't always ask for it by default.

Fix: append ?sslmode=require to the external URL. And never give the hosted app the external URL — the internal one is faster, free of this problem, and doesn't leave Render's network.

Boot log says “relation already exists”

blocks deploy

This means migrations ran against a database that has tables but no _migrations history — the classic symptom of deploying before restoring, then restoring schema on top.

Fix: keep the order from Phase 2 — restore the full dump first, deploy second. If you're already tangled: drop and recreate the Render database, restore, redeploy.

Sign-in bounces with a WorkOS error

blocks deploy

The redirect URI in the env var and the one allowlisted in the WorkOS dashboard must match exactly — scheme, host, path. One character off (http vs https, a trailing slash) and WorkOS refuses.

Fix: copy-paste the same string into both places. Add the custom domain's callback too if you later attach one.

Sign-in works, then “not invited”

annoyance

Working as designed: being able to authenticate with WorkOS is not the same as being invited. The email must exist in app_users, which came over in your restore — so this usually means a teammate signed in with a different email than the one on file.

Fix: node server/cli.js user:add name@karmastaff.com member (with DATABASE_URL pointed at the external URL).

Pipeline gets 401 / 403

annoyance

Either KARMA_API_TOKEN isn't set in the shell running sync.py, or the token was minted against the wrong database (local vs hosted — the token lives in the database it was minted against), or someone tried to use the import token for a non-import endpoint, which it can never reach by design.

Fix: re-mint against the Render URL (Phase 5) and re-set both env vars in the same window.

Picking free-tier Postgres to save money

data risk

Render deletes free Postgres instances after 30 days. On day 31 the leads, the users, the activity log, and every lead code would be gone. This is the single most expensive $6/month you could ever save.

Fix: smallest paid tier from day one. Your ~35k leads occupy a few megabytes; the smallest plan is already oversized.

Running an import while unsure where it's pointed

data risk

During the parallel-run week both databases exist. An import aimed at the wrong one splits your data's history in two, and un-splitting it is manual work.

Fix: echo $env:KARMA_API_URL before every run, and always --dry-run first — the plan it prints tells you which world you're about to change. After cutover week, stop the local stack so there's only one target left.

05

A one-week timeline that can't hurt you

The trick that makes this migration safe for a beginner: never turn the old system off to turn the new one on. Your local stack keeps running untouched all week. Render starts as a copy; the team moves over only after it has proven itself; and “rollback” is never more dramatic than telling the team to use the old address again.

Saturday≈ 2 h
Build it: Phases 0–2. Accounts, database, restore. Nothing the team uses has changed.
Sunday≈ 2 h
Light it up: Phases 3–4. Deploy, health check, WorkOS callback. Sign in yourself, click through every tab, open leads, leave a note. You are the only user who knows this exists.
Monday≈ 15 min
One volunteer: give a single teammate the Render URL. Real work, real edits — on the new system. Everyone else stays local. Watch the Team activity tab and Render's logs.
Tue – Wed
Whole team on Render: share the URL with everyone; the local stack keeps running as the safety net. Any serious problem → team goes back to the old address, you debug without pressure.
Thursday≈ 30 min
Move the pipeline: Phase 5. First hosted sync.py --dry-run, then the real run. From here, new leads land on Render — the moment of true cutover.
Weekend≈ 30 min
Retire and protect: stop serving the app locally (keep Docker Postgres around for a few weeks as a cold spare), set up the backup task (Phase 6), and do the one test restore.

The one rule of the week: during days when both systems exist, edits made on one do not appear on the other. That's fine for a trial day — but it's why the pipeline moves last, after the team has committed, and why the local stack is retired promptly after: a safety net you never jump into on purpose.

06

Glossary for the words this guide leans on

Environment variable
A named value handed to a program by whatever starts it, instead of written in a file. How cloud platforms pass secrets and settings without putting them in code.
Managed Postgres
A database Render runs for you — they patch it, back it up daily, and hand you a connection URL. You bring only your data.
Internal vs external URL
Two addresses for the same database: internal works only between your Render services (fast, private — for the app); external works from anywhere with SSL (for you and your scripts).
pg_dump / pg_restore
Postgres's export and import tools. A “dump” is a complete, restorable copy of a database in one file.
Stateless
A server that keeps no memory of its own between restarts — everything durable lives in the database. The property that makes cloud hosting safe.
Health check
A URL the platform polls to ask “are you alive?”. Anything but a quick 200 response and the platform restarts your app.
Service token
A password for a program instead of a person — here, klsvc_…, which can only submit imports and can be revoked without touching any human account.
Parallel run
Operating the old and new systems side by side so the new one can fail safely while the old one still works.
